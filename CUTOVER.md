# Односторонний переезд на v2

План без ветки staging, без второго бота и без пути назад. Занимает 1–1,5 часа.

Ключевое отличие от плана с откатом: **вся проверка переносится на этап до
деплоя**. После шага 7 исправлять что-либо придётся уже вперёд, а не назад,
поэтому шаг 5 пропускать нельзя ни при каких обстоятельствах.

Не начинайте, если в ближайшие 3 часа запланирован квиз.

---

## 1. Копия таблицы

В Google-таблице: **Файл → Создать копию**, назовите `quiz_backup_2026-08-09`.
Затем **Файл → Скачать → Microsoft Excel (.xlsx)**, сохраните локально.

Это не механизм отката — это источник данных на случай, если миграция
перенесёт историю не полностью. Пять минут.

## 2. Зафиксируйте эталонные цифры

Откройте оба лидерборда и в боевых группах выполните `/rating` и `/stats`.
Сохраните вывод — с ним будете сверяться на шаге 5.

Конкретно нужны: топ-5 игроков с очками в каждой из двух групп и общее
количество строк данных в листе `Games` (без шапки).

## 3. Замените код

```bash
git checkout main
git pull
```

Удалите старый `bot.py` и положите в корень новые файлы:

```
bot.py  config.py  db.py  engine.py  game.py  packs.py  scheduler.py
sheets.py  texts.py  handlers_admin.py  handlers_stats.py
migrate_from_sheets.py  requirements.txt  runtime.txt  Procfile
```

Папка `packs/` не трогается. Добавьте в `.gitignore`:

```
*.db
*.db-wal
*.db-shm
```

Закоммитьте, но **не пушьте** — деплой будет на шаге 7.

```bash
git add -A && git commit -m "v2: SQLite, планировщик, рефакторинг"
```

## 4. Том на Railway

1. Command Palette (⌘K) → **New Volume** → сервис бота → mount path `/data`.
2. Railway передеплоит сервис (пока ещё со старым кодом из main — это нормально).
3. Проверьте: `railway volume files list /` отрабатывает без ошибки.

## 5. Миграция и сверка — главный шаг

Миграция запускается локально: `railway run` подставляет переменные окружения
сервиса в ваш процесс, а не выполняет код в контейнере.

```bash
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
railway link                                   # выберите проект и сервис
railway run env DB_PATH=./quiz.db PACKS_DIR=./packs python migrate_from_sheets.py
```

Ожидаемый вывод:

```
INFO | Строк получено: 3847
INFO | Уникальных игр: 214
INFO | Готово. Импортировано игр: 214, пропущено как дубли: 0
```

### Сверка №1 — объём

```bash
sqlite3 quiz.db "
  SELECT 'игр', COUNT(*) FROM games
  UNION ALL SELECT 'результатов', COUNT(*) FROM results;
"
```

Число «результатов» обязано совпасть с количеством строк данных в `Games`
из шага 2. Расхождение больше нуля — стоп.

### Сверка №2 — содержание

```bash
sqlite3 -column -header quiz.db "
  SELECT username, COUNT(*) AS игр, SUM(rating_points) AS очки
  FROM results WHERE chat_id = -1002440363847
  GROUP BY username ORDER BY очки DESC LIMIT 5;
"
```

Повторите для `-1003453018572`. Оба топ-5 должны совпасть с эталоном из шага 2.

### Сверка №3 — предупреждения

Пересмотрите лог миграции на строки `Пропущена игра с датой ...`. Каждая
такая строка — потерянная игра.

**Если любая из трёх сверок не сошлась — остановитесь и разберитесь.**
Сейчас это стоит нисколько: ничего не задеплоено, старый бот работает.
После шага 7 та же проблема будет стоить ручного восстановления из .xlsx.

## 6. Подготовьте файл базы

```bash
sqlite3 quiz.db "VACUUM INTO 'quiz-upload.db';"
railway volume files upload ./quiz-upload.db /quiz.db
railway volume files list /
```

Пути указываются от корня тома: `/quiz.db` внутри контейнера доступен как
`/data/quiz.db`.

Локальный `quiz.db` не удаляйте — это ваш единственный снимок данных на
момент переезда.

## 7. Деплой

С этого момента возврата нет. Между шагом 5 и этим моментом квизов быть не
должно — иначе новые игры попадут в `Games`, но не в SQLite. Если такое
всё-таки случилось, просто повторите шаги 5–6: скрипт идемпотентен и
подтянет только недостающее.

```bash
git push origin main
```

В логах Railway должно появиться:

```
INFO  db  | SQLite готов: /data/quiz.db
INFO  scheduler | Планировщик запущен, период 60 с
INFO  bot | 🚀 Бот запущен
```

Если вместо этого видите `SQLite готов: ./quiz.db` — том не подхватился,
проверьте переменную `DB_PATH` и mount path.

## 8. Проверка на живом боте

Сразу в боевой группе:

```
/rating
/stats
```

Сверьте с эталоном шага 2. Затем откройте оба HTML-лидерборда — формат листов
и время в сотых долях не менялись, они должны работать без правок.

В личке боту:

```
/games
/history
```

В `/history` процент правильных ответов должен быть в диапазоне 60–90%, а не
0.8% — это тот самый исправленный баг с делением на 100.

## 9. Первый квиз — вручную

```
/quiz 0007 | 2026-08-10 | 20:00
```

Не через расписание. Пройдите весь цикл и убедитесь, что:

- варианты перемешаны, верный засчитывается;
- промежуточный рейтинг появляется раз в 4 вопроса (так задумано — раньше был
  после каждого, это упиралось в лимит Telegram);
- после квиза в `Games` появились строки, «Очки рейтинга» — последняя колонка
  после 16 блоков вопросов.

## 10. Расписание — после двух-трёх успешных квизов

```
/schedule add пн,ср,пт | 20:00 | auto | 60
/schedule
```

Четвёртый параметр — за сколько минут открывать регистрацию. Проверьте, что в
назначенное время регистрация открылась сама, и только потом настраивайте
вторую группу.

## После переезда

Google Sheets остаётся витриной: лидерборды продолжают читать `gviz/tq`,
формат колонок прежний. Первичное хранилище теперь SQLite.

Бэкап раз в неделю:

```bash
railway volume files download /quiz.db ./backups/quiz-$(date +%F).db
```

Два правила эксплуатации:

- не деплойте во время квиза — редеплой сервиса с томом даёт короткий простой;
  результаты сохранятся, но текущий вопрос оборвётся;
- держите одну реплику — SQLite не шарится между инстансами, и polling у
  Telegram может быть только один.
